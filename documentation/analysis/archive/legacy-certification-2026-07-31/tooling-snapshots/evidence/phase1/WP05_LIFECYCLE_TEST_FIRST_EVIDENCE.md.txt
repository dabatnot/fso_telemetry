# Phase 1 WP05 lifecycle test-first evidence

Status: **the initial WP05 lifecycle contract was independently RED before
production implementation; independent reviewer-strengthening oracles were also
RED before their corrective production patches; final review is pending GREEN
evidence**. This file distinguishes the initial structural RED from the later
review RED instead of retroactively claiming that every strengthened oracle
existed before the first production draft.

`G1-D` remains OPEN. WP05 provides process/runtime and mission lifecycle
foundations only; it does not implement WP06 negotiation, live client sessions,
heartbeat, ACK/NACK, ingress policy, quotas, replication or Phase 2 events.

## Frozen lifecycle interpretation

The tests freeze the following decisions without changing the public API
`void telemetry::initialize() noexcept`:

1. `GameMissionLoad` discards its `const char*` argument at the wrapper boundary.
   The runtime callback has no filename parameter. A poison pointer
   `reinterpret_cast<const char*>(1)` is emitted by the isolated integration test;
   it must not be read, copied, logged or forwarded. The callback immediately
   blocks mission publication through a value latch, but physical purge occurs on
   the next captured-main-thread `EngineUpdate`.
2. Repeated loads before that tick coalesce into one purge and one generation.
   `mission_generation` is `uint32_t`, begins at zero, becomes one on the first
   applied load, and advances once per distinct applied load. Leave/reentry does
   not increment it. Overflow must not wrap: it performs fail-closed resource
   teardown and leaves the runtime terminal `Faulted`.
3. Lifecycle callbacks retain only old/new integer values and bounded value
   latches. Their side effects are delayed one frame because `EngineUpdate`
   precedes game-sequence event processing. The latches preserve observation
   order without a queue: Load then Terminal ends `Ready`, Terminal then Load
   ends `MissionLoading`, and Terminal then Load then `GAME_PLAY` ends
   `MissionActive`; each sequence performs one purge and applies at most one
   coalesced load generation.
4. `GAME_PLAY` is the sole active root and may activate only an already-open
   `MissionLoading` generation. `Ready -> GAME_PLAY` is invalid and faults; no
   loading/briefing/selection/sync screen may invent a mission without an applied
   `GameMissionLoad`.
5. A wrong-thread callback may perform only thread-identity comparison and a
   defensive invariant latch. It invokes no service, engine global, diagnostic,
   purge or transport hook. The test joins its worker, observes immediate
   publication denial, then requires teardown and one diagnostic at the next
   captured-main-thread update. An atomically readable callback-inert gate must
   be checked before any non-atomic runtime-state fast path so callbacks racing
   with `ShuttingDown` or arriving after `Stopped` cannot read mutable state or
   arm the violation latch. The gate and relaxed violation latch are defensive
   scalars, not a worker architecture, queue, mutex, condition variable or
   functional cross-thread data path.
6. Mission purge order is collection prohibition, mission/entity invalidation,
   replication cancellation, session/store closure, then mission-scope reset.
   Listener/transport and the process session-ID registry remain alive.
7. Shutdown order is collection prohibition, sessions/stores, mission/entities,
   transport, at most one final summary, runtime allocations, registry, then
   `Stopped`. Fault cleanup follows the same resource order without the shutdown
   summary and emits one diagnostic after cleanup. There is no drain, final ACK,
   sleep or join.
8. `RuntimeTransportStatus::Started` exists only for deterministic fakes in WP05.
   The native adapter remains blocked by the incomplete startup-budget mask
   `0x00fb`; WP05 must not bind a real socket or publish a client `session_id`.
   The registered startup candidate is observable only by the fake, while
   `published_session_id()` remains zero in `Ready` and `MissionActive`.

## Exhaustive engine-state partition

The ordinary unit test contains an array with exactly `GS_NUM_STATES == 56`
entries and a compile-time guard. Adding or removing an engine state therefore
requires an explicit lifecycle review.

- `Invalid`: `GS_STATE_INVALID`, negative values and values greater than or equal
  to `GS_NUM_STATES`; these fault without clamping or engine-global reads.
- `ActiveRoot`: `GS_STATE_GAME_PLAY` only, and only from an applied loading
  generation.
- `PreserveContext`: `GAME_PAUSED`, `DEBUG_PAUSED`, `TRAINING_PAUSED`,
  `MULTI_PAUSED`, `OPTIONS_MENU`, `HOTKEY_SCREEN`, `GAMEPLAY_HELP`,
  `MISSION_LOG_SCROLLBACK`, `HUD_CONFIG`, `CONTROL_CONFIG`, `INGAME_OPTIONS`,
  `SHOW_GOALS`, `DEATH_DIED`, `DEATH_BLEW_UP`, `EVENT_DEBUG`, `LAB` and
  `SCRIPTING_MISSION`. These preserve the current `Ready`, `MissionLoading` or
  `MissionActive` context and never promote it.
- `LoadingPreserve`: `LOAD_MISSION_MENU`, `BRIEFING`, `CMD_BRIEF`, `LOOP_BRIEF`,
  `SHIP_SELECT`, `WEAPON_SELECT`, `TEAM_SELECT`, `MULTI_MISSION_SYNC`,
  `MULTI_START_GAME`, `INGAME_PRE_JOIN`, `RED_ALERT`, `FICTION_VIEWER`,
  `MULTI_STD_WAIT`, `START_GAME` and `MULTI_HOST_OPTIONS`. These retain an
  already-open load; from `Ready` they stay `Ready`, and from `MissionActive`
  they cause a discontinuity and return to `Ready` unless a load is pending.
- `Terminal`: all remaining named states; from a mission they purge to `Ready`.

Death states are deliberately state-preserving and synthesize no business event.
The services seam has a compile-time negative check for `emit_event_batch`; death,
observer and respawn events remain Phase 2 under `D1-012`.

## Superseded WP03 wrong-thread interpretation

The former WP03 test named `WrongThreadFaultsBeforeConfigurationAndNeverRetries`
used `main_thread_matches=false` in a service fake and expected a service call and
immediate diagnostic in the same invocation. WP05 supersedes that interpretation:
a real worker must call no service and cleanup is deferred. The old test is
renamed `StartupThreadServiceMismatchFaultsBeforeConfigurationAndNeverRetries`;
it now covers only an inconsistent startup-service observation while the caller
itself remains on the captured C++ thread. The real wrong-thread contract is
`WP05-LC-009`.

## Independent reviewer-strengthening RED

The first production draft passed the original Debug oracle, but the independent
Release run exposed a deterministic reentrant-shutdown defect:

```powershell
.\build\bin\Release\unittests.exe --gtest_color=no `
  --gtest_filter=TelemetryRuntimeLifecycleContract.*:TelemetryRuntimeStartupContract.*
```

Exit code: `1`; `30/31` passed. The failing
`ReentrantShutdownWhileShuttingDownIsANoopAndSummaryRemainsUnique` recorded two
complete teardown tails and two runtime summaries. Production work was paused
while the reviewer oracle was expanded.

The expanded Debug filter then executed eight order/reentrance tests. Exit code:
`1`; `2/8` passed and these six failed before corrective production changes:

- Terminal then MissionLoad ended `Ready` instead of `MissionLoading`;
- shutdown from `purge_mission` resumed four outer hooks, advanced the generation
  and resurrected `MissionLoading`;
- shutdown from fault cleanup resumed five outer hooks and emitted a diagnostic
  after `Stopped`;
- shutdown from the startup thread check, registry rollback for both allocation
  and registration failure, and both transport-failure cleanup hooks resumed as
  `Faulted` and emitted a diagnostic after `Stopped`.

The separate real-worker oracle executed each callback from inside the first
shutdown hook after the runtime had entered `ShuttingDown`:

```powershell
.\build\bin\Debug\unittests.exe --gtest_color=no `
  --gtest_filter=TelemetryRuntimeLifecycleContract.EveryCallbackIsAtomicallyInertThroughoutShuttingDown
```

Exit code: `1`; `0/1` passed. MissionLoad, Enter and Leave (callback indices 2,
3 and 4) armed the wrong-thread latch instead of observing an atomic inert gate.
Update and Shutdown happened to return early, but did so through a non-atomic
state read; the common gate is therefore required for all five callbacks.
These results are the preserved reviewer RED boundary for `WP05-LC-011` through
`WP05-LC-013`.

Two subsequent order-composition filters were frozen before their respective
corrective patches. Each exited `1` with `0/2` passing:

- Terminal, ActiveRoot, then PreserveContext incorrectly ended `Ready` instead
  of preserving the pending `MissionActive` destination; Load, Terminal, then
  LoadingPreserve incorrectly resurrected `MissionLoading` instead of remaining
  `Ready`;
- Terminal, ActiveRoot, then LoadingPreserve incorrectly remained
  `MissionActive` instead of converging `Ready`; from `Ready`, Load, Terminal,
  then ActiveRoot incorrectly reused the closed historical load, published
  `MissionActive` generation 1 and avoided the required
  `InvalidLifecycleTransition` fault.

The paired contrasts Terminal, Load, LoadingPreserve and Terminal, Load,
ActiveRoot remain valid loading/active destinations. Together these cases close
the bounded, queue-free destination summary required by specification 03 section
6.1 rather than accepting a latest-state-plus-boolean approximation.

The review then isolated the final continuity distinction in one table-driven
oracle. Before its corrective patch the exact Debug filter exited `1`:

- initial `MissionActive`, Load, Terminal, ActiveRoot incorrectly published a
  second active generation instead of faulting with the original generation
  unchanged;
- initial `Ready`, Load, ActiveRoot, Terminal, ActiveRoot incorrectly faulted
  instead of keeping the newly established active continuity and generation 1;
- initial `MissionActive`, Load, ActiveRoot, Terminal, ActiveRoot and the no-load
  Terminal/ActiveRoot reentry were already valid contrasts.

This RED requires only a bounded pending destination plus a boolean recording
whether ActiveRoot established continuity since the latest Load; Load clears it,
a valid ActiveRoot sets it, and Terminal may preserve that same-tick evidence.
It does not authorize a marker queue.

Finally, the simulated-destination purge oracle started from stable
`MissionLoading`, observed ActiveRoot then LoadingPreserve, with and without a
final ActiveRoot reentry. Before correction both blocks reached the expected
final state but recorded an empty service trace instead of exactly one
`MissionPurgeOrder`; the focused Debug filter exited `1`. This RED proves that
the discontinuity predicate must use the destination immediately before the
LoadingPreserve marker, not the still-deferred stable `m_state`.

whitespace scan found no match.
